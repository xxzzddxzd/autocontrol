# autocontrol 接入规范 v1（脚本作者版）

本文写给要把自己的 Python 自动化脚本接入总控台的作者，只写你要对接和改造的部分。调度、卡片、通知、归档、指标都由总控台负责，你不需要了解它们怎么实现。

- Python SDK：`sdk/python/autocontrol_worker.py`（单文件，只依赖标准库，复制到脚本旁边即可）
- 完整示例：`examples/demo_worker/`（清单 + 脚本，可离线运行并通过准入）
- JSON Schema：`docs/schemas/manifest.schema.json`、`event.schema.json`、`result.schema.json`；协议以 `autocontrol/protocol.py` 为准

---

## 1. 分工

| 总控台负责（你不用做） | 脚本负责（你要做） |
|---|---|
| 按时刻启动脚本、补跑、互斥、超时终止 | 读取实时状态，决定做什么，执行，回读确认 |
| 飞书卡片和所有通知 | 通过进度事件和最终结果如实上报每个任务的状态 |
| 结果归档、运行指标、准入检查 | 遵守协议：退出码、最后一行结果、只读模式 |

### 你不需要做的

- **调度和唤醒**：不写定时器、cron 或常驻循环。固定时刻写在清单 `schedule.times` 里；服务器计时到期的时刻放进结果的 `next_wake`。
- **决定何时重试**：失败、受阻、超时的任务如实上报即可，下一轮会再运行。本轮不要循环重试同一个变更请求。
- **超时和杀进程**：总控台负责计时，到点先发 SIGTERM，5 秒后 SIGKILL。你只需按截止时间收尾（见 B4）。
- **飞书卡片和任何通知**：不发飞书、Lark、webhook、邮件、短信或推送，也不读取总控台的机器人配置（见 B9）。
- **卡片文案、排版和「下次执行」时间**：由总控台根据你上报的状态、原因码和时间生成。
- **结果归档、日志留存、指标存储和告警阈值**：总控台负责。
- **和其他脚本协调**：只需在清单 `account_lock` 声明自己的账号锁。锁被占用时照常立即以退出码 2 退出（见 B3），总控台会每分钟重试这一轮，最长 30 分钟。

> 另一种接入方式是由总控台维护者为大型存量项目编写适配器（例如 yslzm），与本文读者无关。

## 2. 接入步骤

1. 看一遍 `examples/demo_worker/`。
2. 把脚本的功能拆成模块。每个模块对应清单里的一个任务，按第 3 节写清需求方、验收方和今日终点。
3. 按第 4 节写 `autocontrol.json`。
4. 改造脚本：
   - 加一个会话层，各模块只写业务；
   - 用 SDK 上报；
   - 实现只读模式（observe）；
   - 加账号锁，遵守截止时间；
   - 删掉脚本自带的所有通知代码。
5. 本地自测：
   - 直接运行脚本：没有 `AUTOCONTROL_*` 环境变量时，SDK 丢弃事件、照常打印结果；
   - `python3 run.py check --manifest <目录>/autocontrol.json --static` 只校验清单。
6. 准入：反复运行 `python3 run.py check --manifest <目录>/autocontrol.json --repeat 2`，直到必须项全部通过（第 6 节）。
7. 交给总控台维护者试运行和上线。之后**清单任何改动都会使准入失效**，需要重新 `check`；业务代码有实质改动时也应重新 `check`。

## 3. 模块化改造

### 3.1 一个功能一个模块

- 每个功能写成一个模块，对应清单里一个任务（`id` 稳定、不复用，标题是中文）。
- 模块只写业务：**读取实时状态 → 决定还剩什么要做 → 执行 → 回读确认 → 返回最终状态**。
- 模块里不登录、不发通知、不调度、不睡眠等待。

### 3.2 会话层：每次调用只登录一次

- 总控台每次只运行**一个阶段**，即启动一次脚本。
- 这次调用里由会话层登录一次，本阶段所有模块共用同一个会话。
- 只在两种情况下重新登录：会话失效（过期、被踢、服务器要求重新登录）；某个模块需要比之前操作更新的登录状态（例如前一个模块的领取结果只有重新登录后才看得到）。
- 重新登录后要重新读取状态，不沿用旧连接上结果不明的请求。
- 想共用一次登录的模块，放进同一个阶段。

### 3.3 每个任务的需求方、验收方和今日终点

为每个任务先写清这三项，再映射成协议里的状态和原因码（第 5.5、5.6 节）：

| 项目 | 含义 | 示例 |
|---|---|---|
| 需求方 | 谁要求做这件事 | 游戏每日次数上限、日常任务、主页红点可领奖励、服务器当天开放的活动、用户自定的长期目标 |
| 验收方 | 用什么服务器证据确认做完 | 计数器达到上限、任务已领取、可领数量为 0、属性或拥有状态 |
| 今日终点 | 今天做到什么程度算完 | 次数达上限、可领为 0、今天能做的都做完了 |

| 今日情况 | 上报 |
|---|---|
| 达到终点，有服务器证据 | `status: "complete"` |
| 今天能做的都做完了，明天才能继续（长期目标、每日一次的成长、交易上限） | `status: "waiting"`，`reason: "done_for_today"`（卡片算作今日完成） |
| 要等服务器计时 | `status: "waiting"`，给出 `next_run_at`，并把该时刻放进 `next_wake` |
| 条件不满足，本轮不会变（资源不足、未授权） | `status: "blocked"` + 原因码，例如 `insufficient_stamina` |
| 还有可做的部分 | `status: "incomplete"`（有真实分母时给 `current`/`total`） |
| 今天稍后开放 | `status: "waiting"`，`reason: "not_open"`，给出开放时刻 `next_run_at`，并放进 `next_wake` |
| 今天不适用（未开放、无资格） | `status: "closed"`（卡片隐藏、不计数；每天开放不同的活动见 3.6 节） |
| 请求已发出但没收到结果 | `status: "result_unavailable"`，`reason: "request_result_missing"` |

### 3.4 模块必须满足

- **幂等**：完全依据实时状态决定剩余工作；连续运行两次不会多做。
- **不重放**：结果不明的变更请求本轮不再发。需要跨阶段避免重发时，把目标放进 `run_scope`（仅内存，见第 4、5.4 节）。
- **不信任本地标记**：不能用本地「今天做过」文件或总控台卡片跳过业务。
- **有界**：长循环检查 `worker.time_left()`，接近 0 时不再发起新的变更。
- **只读模式零变更**：observe 时只读取，连顺手领取也不行。

### 3.5 代码骨架（SDK）

```python
from autocontrol_worker import EXIT_BUSY, Worker

MODULES = {'signin': run_signin, 'mail': run_mail}  # 模块：(session, worker) -> 最终状态 dict
PHASES = {'daily': ('signin', 'mail')}

def main():
    worker = Worker()
    with account_lock() as locked:                      # B3：脚本自己的账号锁
        if not locked:
            worker.finish('busy', {})
            return EXIT_BUSY
        session = Session.login()                       # 会话层：本次调用只登录一次
        worker.count('sessions').count('reads')
        keys = PHASES.get(worker.phase, tuple(MODULES))  # observe 阶段报全部任务
        worker.plan({key: read_state(session, key) for key in keys})   # 先报计划
        if worker.observe:                              # 只读发现：零变更
            worker.count('actions_sent', 0)
            worker.finish('complete', {key: read_state(session, key) for key in keys})
            return 0
        final = {}
        for key in keys:
            left = worker.time_left()
            if left is not None and left <= 0:          # 到软截止就不再开始新工作
                break
            worker.started(key)
            try:
                state = MODULES[key](session, worker)   # 读 → 做 → 回读确认
            except Exception:                           # 已发出却没有结果时改报 result_unavailable
                state = {'status': 'failed', 'reason': 'action_exception'}
            final[key] = state
            worker.finished(key, **state)
        outcome = 'complete' if all(s['status'] in ('complete', 'closed') for s in final.values()) else 'partial'
        worker.finish(outcome, final)
        return worker.exit_code(outcome)

raise SystemExit(main())
```

模块里每发出一个变更请求调用 `worker.count('actions_sent')`；收到成功回执调用 `count('actions_confirmed')`；明确失败调用 `count('actions_failed')`；没收到结果调用 `count('actions_unconfirmed')`。

一个模块也可以写成 `with worker.task(key) as run:`，结束前用 `run.finish(状态, reason=…, …)` 报回读到的状态。块里抛出异常时自动报 `failed`（原因 `action_exception`）。忘了调用 `finish` 时报 `result_unavailable`（原因 `ended_without_result`），SDK 不会默认报 `complete`。

### 3.6 每天开放不同的活动

服务器每天开放的玩法不一样（限时活动、轮换副本）时，按下面做：

- **清单固定声明所有可能出现的玩法**，任务 ID 稳定。给这些任务加 `"demand": "window"`，表示需求方是「服务器当天开放」。可选再加 `"endpoint"` 写明今日终点：`target` 达到目标、`once` 完成一次、`claim` 领完奖励。
- **每次运行都上报全部声明的任务**（包括只读发现）：

| 当天情况 | 上报 |
|---|---|
| 今天没开放 | `status: "closed"`（卡片不显示、不计数） |
| 今天稍后开放 | `status: "waiting"`，`reason: "not_open"`，`next_run_at` 为开放时刻，并把该时刻放进 `next_wake`（准入 M8） |
| 开放中 | 按 3.3 节正常上报 |
| 已经做完，即使窗口已关闭 | `status: "complete"`，以服务器的参与或奖励记录为证 |
| 窗口已关闭但没做完 | 照常报 `closed`。总控台知道它今天开放过，卡片会显示「已错过 · 今日不执行」，不会把它藏起来 |

- **清单外的新活动不要临时造任务 ID**，未声明的 ID 会被拒绝。声明一个 `"discovery": true` 的「开放活动」任务，用 `counts.unsupported` 上报当天开放、但没有模块处理的活动数：大于 0 时报 `status: "unsupported"`，否则报 `complete`（准入 S5）。`unsupported` 要写进清单的 `count_keys`。
- **不要在进程里等窗口开放**：报 `waiting` 和 `next_run_at`，由总控台按 `next_wake` 唤醒。
- **每日次数上限以服务器读数为准**：总控台每次唤醒都启动一个新进程，记在进程内存里的计数每轮都会清零。

## 4. 接入清单 `autocontrol.json`

```json
{
  "protocol": 1,
  "name": "demo",
  "display_name": "示例脚本",
  "workdir": ".",
  "command": ["{python}", "-B", "worker.py", "{phase}"],
  "phases": ["daily", "shop"],
  "observe_phase": "status",
  "timeouts": {"phase": 300, "observe": 60},
  "schedule": {"timezone": "Asia/Shanghai", "reset": "05:00", "times": ["06:00", "12:00", "20:00"]},
  "account_lock": null,
  "run_scope": false,
  "sections": [{"key": "daily", "title": "日常"}, {"key": "shop", "title": "商店"}],
  "tasks": [
    {"id": "signin", "title": "每日签到", "section": "daily"},
    {"id": "mail", "title": "邮件奖励", "section": "daily"},
    {"id": "mail_read", "title": "读取邮件", "kind": "step", "parent": "mail"},
    {"id": "weekly_pack", "title": "每周礼包", "section": "shop", "kind": "job"}
  ],
  "reasons": {"pack_sold_out": "礼包已售罄"},
  "short_reasons": {"pack_sold_out": "已售罄"},
  "count_keys": ["claimed"],
  "units": []
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `protocol` | 是 | 固定 `1` |
| `name` | 是 | `[a-z][a-z0-9_-]{0,31}`，项目唯一标识 |
| `display_name` | 是 | 1–32 字，卡片标题 |
| `workdir` | 是 | 脚本工作目录，相对清单所在目录 |
| `command` | 是 | 启动命令数组，必须含 `{phase}`；可用占位符 `{phase}`、`{service_day}`、`{mode}`、`{python}` |
| `phases` | 是 | 一轮里各阶段的执行顺序（一个阶段 = 一次调用 = 一次登录） |
| `observe_phase` | 否 | 只读发现所用阶段名，默认 `status`，不能出现在 `phases` 中 |
| `timeouts` | 否 | `phase` 默认 1800 秒，`observe` 默认 180 秒（10–86400） |
| `schedule` | 是 | `times`：固定运行时刻（`HH:MM` 列表）；`reset`：服务日切换时刻，默认 `05:00`（服务日按它大部分时间所在的日期命名：`reset` 早于 12:00 按开始日期，12:00 及以后按次日）；`timezone`：默认 `Asia/Shanghai` |
| `account_lock` | 否 | 脚本自己的账号锁文件（flock）。建议写绝对路径（可用 `~`），和脚本加锁用同一个文件；相对路径以总控台私有目录为基准。总控台开轮前只探测、不持有 |
| `run_scope` | 否 | 设为 `true` 时，上一阶段结果中的 `run_scope` 经 stdin 原样传给下一阶段 |
| `sections` | 是 | 卡片分组：`key` 通常与阶段同名，`title` 1–16 字 |
| `phase_titles` | 否 | 阶段显示名，缺省使用同名分组的标题 |
| `tasks` | 是 | 任务（即模块），顺序就是卡片里的顺序，最多 256 个，规则见下 |
| `reasons` | 否 | 自定义原因码（`[a-z][a-z0-9_]{0,47}`）→ 1–40 字中文说明 |
| `short_reasons` | 否 | 原因码 → 卡片行内短标签（1–8 字）；只能用标准或自定义原因码 |
| `count_keys` | 否 | 允许上报的计数键；未声明的计数会被丢弃 |
| `units` | 否 | 追加计量单位（1–4 字） |

`tasks` 的规则：

- `id` 为 `[a-z][a-z0-9_]{0,39}`，标题 1–20 字。
- `kind`：`goal`（每日目标，默认）、`job`（阶段内的具体工作）或 `step`（子步骤）。`step` 必须给出前面已声明的 goal 或 job 作为 `parent`，**不能证明父任务完成**。
- goal 和 job 必须属于已声明的分组。
- `seed` 默认 goal、job 为 true，表示每天固定在计划里。
- `demand`（可选）：需求方，`daily`（默认）、`weekly`，或 `window`（服务器当天开放才有，见 3.6 节）。
- `endpoint`（可选）：今日终点，`target`、`once` 或 `claim`。
- `discovery`（可选）：最多一个任务设为 true，即「开放活动」发现任务（见 3.6 节）。

`private`（总控台的数据目录）和 `lark_config`（机器人配置）由总控台维护者设定，脚本作者不用写。所有文字字段不能含尖括号、星号、波浪线、反引号、方括号或换行。

以后的版本会以向后兼容的字段增加模块启停、固定时段、每轮收菜等能力，现有清单无需修改。

## 5. 执行器协议 v1

### 5.1 调用约定

- 总控台在 `workdir` 中执行 `command`，每次运行一个阶段。
- 有两种模式：`execute`（执行）和 `observe`（只读发现，阶段名为 `observe_phase`）。

| 环境变量 | 含义 |
|---|---|
| `AUTOCONTROL_PROTOCOL` | `1` |
| `AUTOCONTROL_PROJECT` | 清单 `name` |
| `AUTOCONTROL_PHASE` | 当前阶段 |
| `AUTOCONTROL_MODE` | `execute` 或 `observe` |
| `AUTOCONTROL_SERVICE_DAY` | 目标服务日 `YYYY-MM-DD`，按总控台的命名规则给出。结果和 `plan` 的 `day` 直接用它（SDK 默认如此），不要自己按游戏时区换算 |
| `AUTOCONTROL_RUN_ID` | 本轮标识（同一轮各阶段相同） |
| `AUTOCONTROL_DEADLINE` | 软截止时间（Unix 秒，等于开始时刻 + 超时 − 10 秒）。过了它不再发起新的变更 |
| `AUTOCONTROL_PROGRESS_FD` | 进度管道的文件描述符（SDK 自动使用） |

- **stdin**：`run_scope: true` 时为 `{"run_scope": {...}}`（SDK 放在 `worker.run_scope`），否则为空。
- **stdout**：可以随便打印，但**最后一个非空行必须是最终结果 JSON**（单行，≤ 2 MiB）。stderr 会被丢弃。

### 5.2 退出码

| 退出码 | 何时使用 |
|---|---|
| `0` | 正常结束，最终结果可信（任务可以仍未完成） |
| `1` | 执行失败，结果可能只是部分 |
| `2` | 账号或资源被其他程序占用，**什么都没做** |
| `3` | 配置或前置条件缺失，什么都没做 |

`worker.exit_code(outcome)` 会按结果给出 0、1 或 2；配置错误请自行返回 `EXIT_CONFIG`（3）。

### 5.3 进度事件（用 SDK 发送）

| SDK 调用 | 事件 | 用途 |
|---|---|---|
| `worker.plan(tasks, next_wake=...)` | `plan` | 开始时上报本阶段每个任务当前的完整状态（只读观察） |
| `worker.started(task)` / `worker.progress(task, current, total)` | `task_started` / `task_progress` | 开始处理，以及进度 |
| `worker.finished(task, status, ...)` | `task_finished` | 任务的最终状态（必须带 `status`） |
| `worker.failed(task, reason=...)` | `task_failed` | 失败；也可传 `status="result_unavailable", reason="request_result_missing"` |

- SDK 保证单行不超过 4096 字节、非阻塞写入；写入失败时直接丢弃，不影响业务。
- 不用 SDK 时，需要自己遵守这些规则，并带上 `v`（=1）、`kind`、严格递增的 `seq` 和 `ts`（Unix 秒），格式见 `docs/schemas/event.schema.json`。
- 任务 ID 必须在清单中。

### 5.4 最终结果（stdout 最后一行，`worker.finish(...)` 生成）

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是 | `1` |
| `phase` | 是 | 当前阶段 |
| `day` | 是 | 实际执行的服务日 |
| `outcome` | 是 | `complete`（全部完成或不适用）、`partial`（仍有未完成）、`waiting`（剩余的都在等时间）、`failed`、`busy`（被占用，什么都没做）、`skipped`（前置不满足，无事可做） |
| `failure_stage` | 否 | `config` / `lock` / `login` / `connect` / `read` / `execute` / `write` |
| `error_type` | 否 | 异常类名（`[A-Z][A-Za-z0-9]{0,63}`），**不要**输出异常正文 |
| `tasks` | 是 | 本阶段每个任务的最终状态（busy、skipped 可为空） |
| `next_wake` | 否 | 需要总控台再来检查的未来时刻（Unix 秒，最多 48 个） |
| `metrics` | observe 时必须含 `actions_sent` | 操作指标，见 5.7 |
| `run_scope` | 否 | 仅清单 `run_scope: true` 时生效，≤ 128 KiB，替换后交给下一阶段 |

```json
{"v":1,"phase":"daily","day":"2026-11-17","outcome":"waiting","tasks":{"signin":{"status":"complete"},"mail":{"status":"complete","counts":{"claimed":2}},"energy":{"status":"waiting","current":1,"total":3,"next_run_at":1763344800}},"next_wake":[1763344800],"metrics":{"actions_sent":3,"actions_confirmed":3,"reads":1}}
```

### 5.5 任务状态（十种）

每个任务的状态对象可含：`status`、`reason`（原因码）、`current`/`total`（非负整数；**只有真实分母时才给 `total`**）、`unit`、`next_run_at`（Unix 秒）、`counts`（键必须在 `count_keys` 中）。

| `status` | 含义 |
|---|---|
| `not_started` | 计划内，尚未处理 |
| `running` | 正在处理 |
| `incomplete` | 部分完成，或仍有可做的部分 |
| `waiting` | 需要等时间（服务器计时、刷新、恢复）；也用于今日已做完（`done_for_today`） |
| `blocked` | 条件不满足（资源不足、未授权等），本轮不再尝试 |
| `complete` | 有服务器证据表明已完成 |
| `failed` | 明确失败 |
| `result_unavailable` | 结果未知：请求已发出未收到结果，或状态读取失败 |
| `unsupported` | 发现了目标，但没有处理流程 |
| `closed` | 今日不适用（未开放、无资格） |

### 5.6 原因码

标准原因码可直接使用：

| 原因码 | 说明 | 原因码 | 说明 |
|---|---|---|---|
| `request_result_missing` | 请求已发出，但未收到结果 | `insufficient_currency` | 货币不足 |
| `action_exception` | 执行时发生异常，未收到成功结果 | `insufficient_stamina` | 体力不足 |
| `timeout` | 执行超时，尚未收到结果 | `insufficient_items` | 道具不足 |
| `session_interrupted` | 会话已中断 | `insufficient_materials` | 材料不足 |
| `session_unavailable` | 当前会话不可用，尚未执行 | `waiting_for_refresh` | 等待服务器刷新 |
| `state_unavailable` | 服务器尚未提供该项状态 | `waiting_for_completion` | 等待服务器任务到期 |
| `login_required` | 需要重新登录 | `waiting_for_stamina` | 等待体力恢复 |
| `captcha_required` | 需要人工验证 | `not_open` | 尚未开放 |
| `rate_limited` | 请求过于频繁 | `forbidden` | 当前授权或规则不允许执行 |
| `server_maintenance` | 服务器维护中 | `config_missing` | 缺少配置或凭据 |
| `unsupported` | 发现目标，但尚无处理流程 | `done_for_today` | 今日已无可做，明日继续 |

其他原因码写在清单 `reasons` 里。原因码只能是枚举值，**不允许**放服务器消息、异常正文等自由文本。

`window_ended`（今天的开放时段已结束，未完成）由总控台生成，脚本不用上报。

### 5.7 单位、计数与操作指标

- 标准单位：次、项、个、份、轮、件、套、步、封、张、点、宝箱、派遣；其他单位在清单 `units` 中声明。
- 计数只接受 `count_keys` 中的键，值为非负整数。

结果 `metrics` 中的操作指标（非负整数）：

| 键 | 含义 |
|---|---|
| `actions_sent` | 发出的变更请求数（领取、购买、提交等）。**observe 时必须上报且为 0** |
| `actions_confirmed` | 收到成功回执的变更请求数 |
| `actions_failed` | 被明确拒绝或失败的变更请求数 |
| `actions_unconfirmed` | 已发出但未收到结果的变更请求数 |
| `reads` | 只读查询请求数 |
| `retries` | 重试次数（含重连） |
| `sessions` | 本次新建的登录会话数 |

## 6. 自检与准入

```bash
python3 run.py check --manifest <目录>/autocontrol.json --static     # 只校验清单
python3 run.py check --manifest <目录>/autocontrol.json --repeat 2   # 只读真实运行两次并打分
```

- `--private <临时目录>` 可以把准入记录写到别处，用于自测。
- 必须项全部通过才会写入准入记录。记录绑定清单内容，清单一改就要重新检查。

### 6.1 自动检查

| 编号 | 级别 | 检查项 |
|---|---|---|
| M1 | 必须 | 接入清单合法（字段、ID、分组、父子关系、调度、占位符） |
| M2 | 必须 | 工作目录存在，启动命令可找到 |
| M3 | 必须 | 只读发现正常结束（退出码 0，未超时、未失败、未被占用） |
| M4 | 必须 | 最终结果符合协议（任务 ID、状态、原因码、单位、计数、指标都合法） |
| M5 | 必须 | 进度事件符合协议：至少一个 `plan`，没有被拒绝的事件，`seq` 递增 |
| M6 | 必须 | 计划覆盖清单中全部固定（`seed`）任务 |
| M7 | 必须 | 只读模式未发出变更请求（`metrics.actions_sent` 存在且为 0） |
| M8 | 必须 | 窗口型任务报 `waiting` 时带 `next_run_at`，且该时刻在 `next_wake` 中（没有窗口型任务时自动通过） |
| S1 | 建议 | 没有输出协议外的字段 |
| S2 | 建议 | 只读发现耗时不超过 `timeouts.observe` 的一半 |
| S3 | 建议 | 结果含 `actions_sent` 和 `reads` |
| S4 | 建议 | 两次只读发现报告的任务集合一致（`--repeat 2`）。每天开放的活动不同不影响：任务集合固定，变的只是状态 |
| S5 | 建议 | 有窗口型任务时，清单声明了 `discovery` 任务，且只读发现上报了它 |

### 6.2 行为要求（评审确认，自动检查无法证明）

| 编号 | 要求 |
|---|---|
| B1 实时读取 | 每次运行都重新读取服务端实时状态来决定做什么；不得依据总控台卡片、归档、指标或本地「今天做过」标记跳过业务 |
| B2 不重放 | 结果不明的变更请求本轮不得重发，如实上报 `result_unavailable` + `request_result_missing`；跨阶段避免重发用 `run_scope` |
| B3 资源互斥 | 同一账号或资源用互斥锁（建议 flock，并在清单 `account_lock` 声明）；被占用时以退出码 2 退出且不做任何事，不开第二个会话 |
| B4 有界执行 | 总时长小于 `timeouts.phase`；过了 `AUTOCONTROL_DEADLINE` 不再发起新的变更；收到 SIGTERM 后 5 秒内退出，不再发起变更；循环有上限 |
| B5 只读模式 | observe 时零变更请求（包括顺手领取），并上报完整计划 |
| B6 如实上报 | `complete` 必须有服务器证据；部分完成用 `incomplete`；未知用 `result_unavailable`；不适用用 `closed`；不估算进度 |
| B7 隐私 | 事件、结果、退出码里不出现账号、令牌、Cookie、手机号、服务器原始响应、异常正文、用户输入，只用枚举码和数字 |
| B8 服务日 | 以服务器服务日为准返回 `day`；跨服务日的任务归属开始时的服务日 |
| B9 不发通知 | 不自行发送任何通知（飞书或 Lark 机器人、webhook、邮件、短信、推送等），不读取 `lark_config` 等总控台的通知配置；要让人看到的信息只通过事件和结果上报 |

## 7. 卡片与指标

- 总控台根据你上报的状态、原因码、计数和时间，生成每个项目每天一张的飞书卡片，并持续更新。卡片措辞和「下次执行」都由总控台决定，你只需保证上报准确。
- 运行指标（成功率、超时率、协议违规、未确认请求占比等）由总控台记录并按阈值监控（`python3 run.py metrics`）。你只需在结果里报 5.7 节的操作指标。

## 8. 常见问题

- **可以打印日志吗？** stdout 可以，但最后一行必须是结果；stderr 会被丢弃。自己写的日志文件同样要遵守 B7。
- **一个阶段失败了会怎样？** 记为失败，后续阶段照常运行，不会重放；下一轮会再来。
- **怎么让总控台在某个时刻再来？** 在 `plan` 或结果里上报 `next_wake`；任务级时刻用 `next_run_at` 并同时放进 `next_wake`。
- **原脚本自带的日报、提醒怎么办？** 全部删掉（B9），改为上报任务状态、原因码和计数。
- **清单改了要做什么？** 重新运行 `check`。未重新准入前，总控台不会调度执行这个脚本。
