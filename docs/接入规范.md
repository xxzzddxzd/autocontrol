# autocontrol 接入规范 v1（脚本作者版）

本文写给要把自己的 Python 自动化脚本接入总控台的作者，只写你要对接和改造的部分。调度、进度展示、通知、归档、指标都由总控台负责，你不需要了解它们怎么实现。

- Python SDK：`sdk/python/autocontrol_worker.py`（单文件，只依赖标准库，复制到脚本旁边即可）
- 完整示例：`examples/demo_worker/`（清单 + 脚本，可离线运行并通过准入）
- JSON Schema：`docs/schemas/manifest.schema.json`、`event.schema.json`、`result.schema.json`；协议以 `autocontrol/protocol.py` 为准

---

## 1. 分工

| 总控台负责（你不用做） | 脚本负责（你要做） |
|---|---|
| 按时刻启动脚本、补跑、互斥、超时终止 | 读取实时状态，决定做什么，执行，回读确认 |
| 进度展示和所有通知 | 通过进度事件和最终结果如实上报每个任务的状态 |
| 结果归档、运行指标、准入检查 | 遵守协议：退出码、最后一行结果、只读模式 |

### 你不需要做的

- **调度和唤醒**：不写定时器、cron、launchd 任务或常驻循环，上线时把脚本原有的这些都撤掉。总控台只有一个常驻进程，统一调度所有项目。固定时刻写在清单 `schedule.times` 里；服务器计时到期的时刻放进结果的 `next_wake`。一个脚本有几种节奏（例如一天四轮的日常，加上每 2 小时一次的循环任务）时，写成一个清单的多套调度，不要拆成两个项目。
- **决定何时重试**：失败、受阻、超时的任务如实上报即可，下一轮会再运行。本轮不要循环重试同一个变更请求。
- **超时和杀进程**：总控台负责计时，到点先发 SIGTERM，5 秒后 SIGKILL。你只需按截止时间收尾（见 B4）。
- **任何通知**：不发飞书、Lark、webhook、邮件、短信或推送，也不读取总控台的通知配置（见 B9）。
- **代码签名和自校验**：不要在脚本里做代码签名、重签，或者启动、登录前核对自身代码文件的哈希。代码一改、签名没跟上，脚本就会拒绝登录，整轮失败，而且常常是别人改了代码之后才暴露出来。代码变更由准入（清单摘要）和评审把关（见 B10）。
- **进度怎么展示**：文案、排版和「下次执行」时间都由总控台根据你上报的状态、原因码和时间生成。你只管如实上报，不用关心展示在哪里、长什么样。
- **结果归档、日志留存、指标存储和告警阈值**：总控台负责。
- **和其他脚本协调**：只需在清单 `account_lock` 声明自己的账号锁。锁被占用时照常立即以退出码 2 退出（见 B3），总控台会每分钟重试这一轮，最长 30 分钟。

> 另一种接入方式是由总控台维护者为大型存量项目编写适配器（例如 yslzm），与本文读者无关。

## 2. 接入步骤

1. 看一遍 `examples/demo_worker/`。
2. 把脚本的功能拆成模块。每个模块对应清单里的一个任务，按第 3 节写清需求方、验收方和今日终点。
3. 按第 4 节写 `autocontrol.json`。
4. 改造脚本：
   - 加一个会话层，各模块只写业务；
   - 用 SDK 上报；
   - 实现只读模式（observe）；
   - 加账号锁，遵守截止时间；
   - 删掉脚本自带的所有通知代码。
5. 本地自测：
   - 直接运行脚本：没有 `AUTOCONTROL_*` 环境变量时，SDK 丢弃事件、照常打印结果，并且默认只读（observe）。要自测执行阶段，显式设置 `AUTOCONTROL_MODE=execute`；
   - `python3 run.py check --manifest <目录>/autocontrol.json --static` 只校验清单。
6. 准入：反复运行 `python3 run.py check --manifest <目录>/autocontrol.json --repeat 2`，直到必须项全部通过（第 6 节）。
7. 准入通过后交给总控台维护者上线。上线时脚本原来的调度（crontab 行、常驻进程、launchd 任务）和它自带的通知都要撤掉，免得两边都跑；具体操作由维护者按仓库 README「接入新脚本」完成。

   上线以后，**清单任何改动都会使准入失效**，需要重新 `check`；业务代码有实质改动时也应重新 `check`。检查通过后，总控台会在两轮之间自动加载新清单（见第 8 节）。

## 3. 模块化改造

### 3.1 一个功能一个模块

- 每个功能写成一个模块，对应清单里一个任务（`id` 稳定、不复用，标题是中文）。
- 模块只写业务：**读取实时状态 → 决定还剩什么要做 → 执行 → 回读确认 → 返回最终状态**。
- 模块里不登录、不发通知、不调度、不睡眠等待。

### 3.2 会话层：每次调用只登录一次

- 总控台每次只运行**一个阶段**，即启动一次脚本。
- 这次调用里由会话层登录一次，本阶段所有模块共用同一个会话。
- 只在两种情况下重新登录：会话失效（过期、被踢、服务器要求重新登录）；某个模块需要比之前操作更新的登录状态（例如前一个模块的领取结果只有重新登录后才看得到）。
- 重新登录后要重新读取状态，不沿用旧连接上结果不明的请求。
- 想共用一次登录的模块，放进同一个阶段。
- 连接和登录要有自己的短超时（建议不超过 60 秒）。超时报 `session_unavailable`；服务器维护时报 `server_maintenance`，并把预计恢复的时刻放进 `next_wake`。不要一直等到阶段超时（默认 30 分钟），那会占住账号、拖过后面的时刻。

### 3.3 每个任务的需求方、验收方和今日终点

为每个任务先写清这三项，再映射成协议里的状态和原因码（第 5.5、5.6 节）：

| 项目 | 含义 | 示例 |
|---|---|---|
| 需求方 | 谁要求做这件事 | 游戏每日次数上限、日常任务、主页红点可领奖励、服务器当天开放的活动、用户自定的长期目标 |
| 验收方 | 用什么服务器证据确认做完 | 计数器达到上限、任务已领取、可领数量为 0、属性或拥有状态 |
| 今日终点 | 今天做到什么程度算完 | 次数达上限、可领为 0、今天能做的都做完了 |

| 今日情况 | 上报 |
|---|---|
| 达到终点，有服务器证据 | `status: "complete"` |
| 今天能做的都做完了，明天才能继续（长期目标、每日一次的成长、交易上限、要等游戏每日刷新的） | `status: "waiting"`，`reason: "done_for_today"`（算作今日完成） |
| 要等服务器计时 | `status: "waiting"`，给出 `next_run_at`，并把该时刻放进 `next_wake` |
| 条件不满足，本轮不会变（资源不足、未授权） | `status: "blocked"` + 原因码，例如 `insufficient_stamina` |
| 还有可做的部分 | `status: "incomplete"`（有真实分母时给 `current`/`total`） |
| 今天稍后开放 | `status: "waiting"`，`reason: "not_open"`，给出开放时刻 `next_run_at`，并放进 `next_wake` |
| 今天不适用（未开放、无资格） | `status: "closed"`（不显示、不计数；每天开放不同的活动见 3.6 节） |
| 请求已发出但没收到结果 | `status: "result_unavailable"`，`reason: "request_result_missing"` |

- **次数用完就是今天的终点**：模块因为服务器显示次数、额度已用完或可领为 0 而停下时，报 `waiting` + `done_for_today`，达到目标的报 `complete`，不要报 `incomplete`。`incomplete` 的意思是今天还能接着做，总控台会在下一轮再运行它，并显示下次执行时间，所以报 `incomplete` 时要带原因码说明还差什么。模块只覆盖了部分功能时，同样以服务器读数判断今天还能不能做。
- **换日时不一定登录**：换日时刻本来做一次只读读取；如果 90 分钟内就有一轮，换日时不登录，先按清单列出新一天的计划（各项为未开始），由那一轮读取服务器。所以换日后第一轮之前，看不到服务器当天的新状态。
- **换日之后的事属于明天**：游戏每天刷新的时刻写在清单 `schedule.reset`。只能等刷新之后才能继续的，报 `waiting` + `done_for_today`。即使报成 `waiting`，并给出 `reset` 或之后的 `next_run_at`，总控台也按今日已了结处理：算作今日完成（注明换日后继续），不计入今天的未完成。
- **跟着领取时间漂移的计时**（例如派遣完成、领取后 6 小时才能再领）：如果每次都把到期时刻原样放进 `next_wake`，只要有一次在非固定时刻运行，之后每天都会多出额外轮次。不急的计时，把 `next_run_at` 报成会处理它的下一个固定轮次时刻（放进 `next_wake` 也只会并入那一轮，总控台把 120 秒内的唤醒当作同一次）。只有错过就有损失的时刻（窗口开放、上限重置等）才单独唤醒。
- **每轮收菜**（城镇收益、采集、牧场这类在两轮之间重新产出的）：在清单里给任务加 `"demand": "round"`。执行阶段把这一轮能做的做完（收完、体力用完），就给它报 `complete`。总控台按本轮完成计数；同一轮后面再读到新产出，不会把它改回未完成；下一轮重新判断。只有执行阶段对这个任务的上报（任务事件或结果里的 `tasks`）算本轮完成，计划里的读数只是当时的状态。不要给这类任务一直报 `waiting` 等下一次产出，那样白天它永远算未完成。

### 3.4 模块必须满足

- **幂等**：完全依据实时状态决定剩余工作；连续运行两次不会多做。
- **不重放**：结果不明的变更请求本轮不再发。需要跨阶段避免重发时，把目标放进 `run_scope`（仅内存，见第 4、5.4 节）。
- **不信任本地标记**：不能用本地「今天做过」文件或总控台的展示、归档跳过业务。
- **有界**：长循环检查 `worker.time_left()`，接近 0 时不再发起新的变更。
- **只读模式零变更**：observe 时只读取，连顺手领取也不行。
- **花费有硬上限**：购买、抽卡、用付费货币或道具加速等花费，必须有每日硬上限（B11）。上限和今日已用量都以服务器读数为准，不用本地计数代替；读数缺失、重复或日期不对时，一次都不花。余额以服务器回执为准，回执没给余额就停下，不用本地扣减代替。用 `done_text`/`progress_text` 把花了多少显示出来（例如「已买 {purchases}/3 次 · 每次 100 金币」），并在脚本自己的说明里写明花哪种货币、单价和每日上限。
- **新内容不拖垮整个任务**：游戏更新常带来本地配置里没有的新卡、新道具、新活动。查不到的那一项只跳过它，其余照常做；因此没做成的部分报 `incomplete`（还有能做的）或 `blocked`（整项都做不了），原因码用 `config_outdated`。不要因为名单里有一项不认识，就把整个任务报成 `result_unavailable` 或什么都不做。配置表尽量跟着游戏版本更新，例如从客户端补丁里取。

### 3.5 代码骨架（SDK）

```python
from autocontrol_worker import EXIT_BUSY, Worker

MODULES = {'signin': run_signin, 'mail': run_mail}  # 模块：(session, worker) -> 最终状态 dict
PHASES = {'daily': ('signin', 'mail')}

def main():
    worker = Worker()
    with account_lock() as locked:                      # B3：脚本自己的账号锁
        if not locked:
            worker.finish('busy', {})
            return EXIT_BUSY
        session = Session.login()                       # 会话层：本次调用只登录一次
        worker.count('sessions').count('reads')
        keys = PHASES.get(worker.phase, tuple(MODULES))  # observe 阶段报全部任务
        worker.plan({key: read_state(session, key) for key in keys})   # 先报计划
        if worker.observe:                              # 只读发现：零变更
            worker.count('actions_sent', 0)
            worker.finish('complete', {key: read_state(session, key) for key in keys})
            return 0
        final = {}
        for key in keys:
            left = worker.time_left()
            if left is not None and left <= 0:          # 到软截止就不再开始新工作
                break
            worker.started(key)
            try:
                state = MODULES[key](session, worker)   # 读 → 做 → 回读确认
            except Exception:                           # 已发出却没有结果时改报 result_unavailable
                state = {'status': 'failed', 'reason': 'action_exception'}
            final[key] = state
            worker.finished(key, **state)
        outcome = 'complete' if all(s['status'] in ('complete', 'closed') for s in final.values()) else 'partial'
        worker.finish(outcome, final)
        return worker.exit_code(outcome)

raise SystemExit(main())
```

模块里每发出一个变更请求调用 `worker.count('actions_sent')`；收到成功回执调用 `count('actions_confirmed')`；明确失败调用 `count('actions_failed')`；没收到结果调用 `count('actions_unconfirmed')`。只报 `actions_sent`、一个回执计数都不报的运行，未确认请求占比记为「无数据」：不判失败，也不算达标。报了确认数或失败数、没报未确认数时，未确认数按「发出 − 确认 − 失败」推算。

一个模块也可以写成 `with worker.task(key) as run:`，结束前用 `run.finish(状态, reason=…, …)` 报回读到的状态。块里抛出异常时自动报 `failed`（原因 `action_exception`）。忘了调用 `finish` 时报 `result_unavailable`（原因 `ended_without_result`），SDK 不会默认报 `complete`。

### 3.6 每天开放不同的活动

服务器每天开放的玩法不一样（限时活动、轮换副本）时，按下面做：

- **清单固定声明所有可能出现的玩法**，任务 ID 稳定。给这些任务加 `"demand": "window"`，表示需求方是「服务器当天开放」。可选再加 `"endpoint"` 写明今日终点：`target` 达到目标、`once` 完成一次、`claim` 领完奖励。
- **开没开放以服务器为准**：每次运行都从服务器读取当天的活动列表或活动状态来判断，不要按脚本里写死的活动列表、日期或上次运行的结果判断，否则活动结束了还会一直算作待做。一个流程要几个活动同时开放时，全部开放才算开放；只需其中一个开放的，有一个开放就算。
- **每次运行都上报全部声明的任务**（包括只读发现）：

| 当天情况 | 上报 |
|---|---|
| 今天没开放 | `status: "closed"`（不显示、不计数） |
| 今天稍后开放 | `status: "waiting"`，`reason: "not_open"`，`next_run_at` 为开放时刻，并把该时刻放进 `next_wake`（准入 M8） |
| 开放中 | 按 3.3 节正常上报 |
| 已经做完，即使窗口已关闭 | `status: "complete"`，以服务器的参与或奖励记录为证 |
| 窗口已关闭但没做完 | 照常报 `closed`。总控台知道它今天开放过，会把它记为「已错过」，不计入进度 |

- **读不到就报未知**：状态读不到时报 `result_unavailable`，或者带 `availability: "unknown"`。总控台不会因此认为窗口今天开放过，窗口关闭后也不会显示「已错过」。窗口关闭时，`complete`、今日已了结（`reason: "done_for_today"`）、结果未知和 `unsupported` 的任务都保持原样。

- **清单外的新活动不要临时造任务 ID**，未声明的 ID 会被拒绝。声明一个 `"discovery": true` 的「开放活动」任务，用 `counts.unsupported` 上报当天开放、但没有模块处理的活动数：大于 0 时报 `status: "unsupported"`，否则报 `complete`（准入 S5）。`unsupported` 要写进清单的 `count_keys`。
- **不要在进程里等窗口开放**：报 `waiting` 和 `next_run_at`，由总控台按 `next_wake` 唤醒。
- **每日次数上限以服务器读数为准**：总控台每次唤醒都启动一个新进程，记在进程内存里的计数每轮都会清零。

## 4. 接入清单 `autocontrol.json`

```json
{
  "protocol": 1,
  "name": "demo",
  "display_name": "示例脚本",
  "workdir": ".",
  "command": ["{python}", "-B", "worker.py", "{phase}"],
  "phases": ["daily", "shop"],
  "observe_phase": "status",
  "timeouts": {"phase": 300, "observe": 60},
  "schedule": {"timezone": "Asia/Shanghai", "reset": "05:00", "times": ["06:00", "12:00", "20:00"]},
  "account_lock": null,
  "run_scope": false,
  "sections": [{"key": "daily", "title": "日常"}, {"key": "shop", "title": "商店"}],
  "tasks": [
    {"id": "signin", "title": "每日签到", "section": "daily"},
    {"id": "mail", "title": "邮件奖励", "section": "daily"},
    {"id": "mail_read", "title": "读取邮件", "kind": "step", "parent": "mail"},
    {"id": "weekly_pack", "title": "每周礼包", "section": "shop", "kind": "job"}
  ],
  "reasons": {"pack_sold_out": "礼包已售罄"},
  "short_reasons": {"pack_sold_out": "已售罄"},
  "count_keys": ["claimed"],
  "units": []
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `protocol` | 是 | 固定 `1` |
| `name` | 是 | `[a-z][a-z0-9_-]{0,31}`，项目唯一标识 |
| `display_name` | 是 | 1–32 字，项目的中文显示名 |
| `workdir` | 是 | 脚本工作目录，相对清单所在目录 |
| `command` | 是 | 启动命令数组，必须含 `{phase}`；可用占位符 `{phase}`、`{service_day}`、`{mode}`、`{python}` |
| `phases` | 是 | 一轮里各阶段的执行顺序（一个阶段 = 一次调用 = 一次登录） |
| `observe_phase` | 否 | 只读发现所用阶段名，默认 `status`，不能出现在 `phases` 中 |
| `timeouts` | 否 | `phase` 默认 1800 秒，`observe` 默认 180 秒（10–86400） |
| `schedule` | 是 | `times`：固定运行时刻（`HH:MM` 列表）；`reset`：游戏每天刷新的时刻，也就是次数、关卡、商店等重置的时间（例如日服 0 点就是北京时间 `23:00`）。总控台按它切换服务日，默认 `05:00`（服务日按它大部分时间所在的日期命名：`reset` 早于 12:00 按开始日期，12:00 及以后按次日）；`timezone`：默认 `Asia/Shanghai`；`phases`：可选，给某些阶段单独的时刻表，限时玩法可以给每个时刻配截止时间 `until`，见下文「多套调度」 |
| `account_lock` | 否 | 脚本自己的账号锁文件，必须用 flock 加锁（总控台用 flock 探测，`lockf` 或 `fcntl` 记录锁它看不到）。建议写绝对路径（可用 `~`），和脚本加锁用同一个文件；相对路径以总控台私有目录为基准。总控台开轮前只探测、不持有，也不会创建这个文件或检查它的权限位 |
| `run_scope` | 否 | 设为 `true` 时，上一阶段结果中的 `run_scope` 经 stdin 原样传给下一阶段 |
| `sections` | 是 | 任务分组：`key` 通常与阶段同名，`title` 1–16 字 |
| `phase_titles` | 否 | 阶段显示名，缺省使用同名分组的标题 |
| `tasks` | 是 | 任务（即模块），顺序就是显示顺序，最多 256 个，规则见下 |
| `reasons` | 否 | 自定义原因码（`[a-z][a-z0-9_]{0,47}`）→ 1–40 字中文说明 |
| `short_reasons` | 否 | 原因码 → 短标签（1–8 字），跟在任务后面显示；只能用标准或自定义原因码。显示了短标签就不再显示进度数字；想看到进度，用任务的 `progress_text` |
| `count_keys` | 否 | 允许上报的计数键；未声明的计数会被丢弃，并记一次协议违规。新计数要先加进清单、准入通过后再上报 |
| `units` | 否 | 追加计量单位（1–4 字）；`错误码`、`负错误码` 有专门用途，见 5.7 节 |

`tasks` 的规则：

- `id` 为 `[a-z][a-z0-9_]{0,39}`，标题 1–20 字，建议不超过 8 个字；同类的小任务能合并就合并。
- `kind`：`goal`（每日目标，默认）、`job`（阶段内的具体工作）或 `step`（子步骤）。`step` 必须给出前面已声明的 goal 或 job 作为 `parent`，**不能证明父任务完成**。
- goal 和 job 必须属于已声明的分组。
- `seed` 默认 goal、job 为 true，表示每天固定在计划里。
- `demand`（可选）：需求方，`daily`（默认）、`weekly`、`window`（服务器当天开放才有，见 3.6 节），或 `round`（每轮收菜，见第 3 节「每轮收菜」）。
- `endpoint`（可选）：今日终点，`target`、`once` 或 `claim`。
- `discovery`（可选）：最多一个任务设为 true，即「开放活动」发现任务（见 3.6 节）。
- `phase`（可选）：执行这个任务的阶段（`phases` 之一），只在它和所在分组不是同一个阶段时填写，子步骤不能填。典型用法见下文「多套调度」：任务列在日常分组，实际由有自己时刻表的阶段执行。总控台仍把它算在日常、按它自己的状态和进度判断完成，下次执行时间按正常轮次加上那个阶段的时刻来算；它上报的 `next_run_at` 也只唤醒那个阶段。
- `done_text`（可选）：完成行文字，接在完成时间后面。例如 `"推进 {cleared} 关 · 当前 {chapter}-{stage}"`显示成「12:10 · 推进 3 关 · 当前 20-1」。用 `{计数名}` 引用 `count_keys` 里的计数（1–4 个），其余文字不超过 24 个字符；引用的计数都报了非负整数才显示，缺一个这段就不显示。总控台用这个任务最近一次上报的整份 `counts`（不合并），所以每次上报都要把引用的计数一起带上；完成时间是当天第一次完成的时间，计数却会被之后每轮的上报替换，要表达当天的结果就报当天累计。
- `progress_text`（可选）：未完成行文字，写法和规则同 `done_text`，例如 `"成功 {claimed} 次 · 剩 {remaining_tickets} 张票"`。任务没完成时，它代替进度数字和原因短标签显示，后面照常接下次执行时间；执行中时显示为「执行中 · 这段文字」。失败、结果未返回、状态未返回、暂无流程这些状态照常显示；引用的计数缺一个，就回到原来的显示。原因的完整说明仍在详情里。

### 多套调度

某些阶段有自己的节奏时，在 `schedule.phases` 里给它单独的时刻表：

```json
"phases": ["commander", "others"],
"schedule": {
  "timezone": "Asia/Shanghai", "reset": "23:00",
  "times": ["00:05", "06:05", "12:05", "18:05"],
  "phases": {"commander": {"times": ["00:00", "02:00", "04:00", "06:00", "08:00", "10:00",
                                     "12:00", "14:00", "16:00", "18:00", "20:00", "22:00"]}}
}
```

- `schedule.times` 只运行没有自己时刻表的阶段；至少要有一个阶段跟着 `schedule.times`。
- 有自己时刻表的阶段只在这些时刻运行。某个时刻没跑成功（失败或账号占用），会在下一个时刻到来前的下一次唤醒里补上。
- 只在短时间开放的限时玩法，给每个时刻配一个截止时间：`{"times": ["18:45"], "until": ["18:57"]}`，`until` 和 `times` 一一对应。截止之前没跑成功的，会在下一次唤醒里补上（也可以用 `next_wake` 让总控台每分钟再来）；过了截止还没成功的时段算错过，不再补跑，下次直接是下一个时刻。不写 `until` 时，时段一直欠到下一个时刻或换日，期间每次唤醒都会补跑。
- 资源用完后没必要照常跑的阶段，可以给它一套低频时刻：`"commander": {"times": [...], "idle": {"reason": "insufficient_materials", "times": ["06:00", "14:00", "22:00"]}}`。这个阶段同名分组里只要有任务最近一次报 `blocked` 且原因是 `reason`，它就只在 `idle.times` 运行，补跑和次数统计也按这套时刻算；之后分组里不再有任务报这个原因（比如资源补上了），就回到 `times`。`reason` 必须是标准或清单里声明过的原因码；低频时刻没有截止时间（`until` 只对 `times` 生效）。这个原因码要专门用来表示「这一阶段没活可干」，分组里别的任务不要因为其他情况报同一个原因。
- 这样的阶段自己报告的服务器时刻（结果里的 `next_wake`，或只读发现结果里它的任务的 `next_run_at`）只唤醒它自己，不会顺带运行其他阶段。写 `"wake": false` 可以关掉。
- 有自己时刻表的阶段按「今天各时刻跑成功了几次」统计，不计入每日完成数；每日完成数只统计其他阶段的任务。
- 和这样的阶段同名的分组里，每个任务都按「今天各时刻是否都跑成功」计完成，不按进度判断。如果一个任务有自己的完成标准和进度（例如每日积分到 100），却要由这个阶段执行，就把它放进日常等分组，再加 `"phase": "commander"` 这样的字段。

`private`（总控台的数据目录）由总控台维护者设定，脚本作者不用写。所有文字字段不能含尖括号、星号、波浪线、反引号、方括号或换行。

以后的版本会以向后兼容的字段增加模块启停、固定时段等能力，现有清单无需修改。

## 5. 执行器协议 v1

### 5.1 调用约定

- 总控台在 `workdir` 中执行 `command`，每次运行一个阶段。
- 有两种模式：`execute`（执行）和 `observe`（只读发现，阶段名为 `observe_phase`）。

| 环境变量 | 含义 |
|---|---|
| `AUTOCONTROL_PROTOCOL` | `1` |
| `AUTOCONTROL_PROJECT` | 清单 `name` |
| `AUTOCONTROL_PHASE` | 当前阶段 |
| `AUTOCONTROL_MODE` | `execute` 或 `observe` |
| `AUTOCONTROL_SERVICE_DAY` | 目标服务日 `YYYY-MM-DD`，按总控台的命名规则给出。结果和 `plan` 的 `day` 直接用它（SDK 默认如此），不要自己按游戏时区换算 |
| `AUTOCONTROL_RUN_ID` | 本轮标识（同一轮各阶段相同） |
| `AUTOCONTROL_DEADLINE` | 软截止时间（Unix 秒，等于开始时刻 + 超时 − 10 秒）。过了它不再发起新的变更 |
| `AUTOCONTROL_PROGRESS_FD` | 进度管道的文件描述符（SDK 自动使用） |

- **stdin**：`run_scope: true` 时为 `{"run_scope": {...}}`（SDK 放在 `worker.run_scope`），否则为空。
- **stdout**：可以随便打印，但**最后一个非空行必须是最终结果 JSON**（单行，≤ 2 MiB）。
- **stderr**：总控台只保留最后 16 KiB，存到私有目录 `logs/<日期>/`（权限 0600，保留 7 天），只供人排查失败，不进展示、指标和结果。可以写异常类型和堆栈，但不要写账号、令牌、Cookie 等凭据。
- **运行环境**：总控台由 launchd 启动，脚本拿到的是精简环境：`HOME`、`USER`、`TMPDIR`、`TZ`（清单的时区）、上表的 `AUTOCONTROL_*`，以及 `PATH=/opt/homebrew/bin:/opt/homebrew/sbin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`。不会加载 `.zshrc` 等 shell 配置，所以：
  - `command` 里的解释器写绝对路径（例如项目自己的 `.venv/bin/python`），或者用 `{python}`（总控台自己的 Python 3.12）；不要依赖 pyenv、nvm 等 shim；
  - 脚本调用的外部程序（dotnet、luajit 等）要能在上面的 `PATH` 里找到，否则写绝对路径；
  - 不要依赖 shell 里设置的环境变量，需要的配置放进脚本自己的配置文件；
  - 没有设置 `LANG`，读写文件时显式写编码；
  - 可以读写 `~/Documents` 下的文件。要访问其他受 macOS 隐私保护的位置或能力（桌面、下载、屏幕录制、辅助功能等），先和维护者确认。

### 5.2 退出码

| 退出码 | 何时使用 |
|---|---|
| `0` | 正常结束，最终结果可信（任务可以仍未完成） |
| `1` | 执行失败，结果可能只是部分 |
| `2` | 账号或资源被其他程序占用，**什么都没做** |
| `3` | 配置或前置条件缺失，什么都没做 |

`worker.exit_code(outcome)` 会按结果给出 0、1 或 2；配置错误请自行返回 `EXIT_CONFIG`（3）。

### 5.3 进度事件（用 SDK 发送）

| SDK 调用 | 事件 | 用途 |
|---|---|---|
| `worker.plan(tasks, next_wake=...)` | `plan` | 开始时上报本阶段每个任务当前的完整状态（只读观察） |
| `worker.started(task)` / `worker.progress(task, current, total)` | `task_started` / `task_progress` | 开始处理，以及进度 |
| `worker.finished(task, status, ...)` | `task_finished` | 任务的最终状态（必须带 `status`） |
| `worker.failed(task, reason=...)` | `task_failed` | 失败；也可传 `status="result_unavailable", reason="request_result_missing"` |

- SDK 保证单行不超过 4096 字节、非阻塞写入；写入失败时直接丢弃，不影响业务。
- 不用 SDK 时，需要自己遵守这些规则，并带上 `v`（=1）、`kind`、严格递增的 `seq` 和 `ts`（Unix 秒），格式见 `docs/schemas/event.schema.json`。
- 任务 ID 必须在清单中。

### 5.4 最终结果（stdout 最后一行，`worker.finish(...)` 生成）

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是 | `1` |
| `phase` | 是 | 当前阶段 |
| `day` | 是 | 实际执行的服务日 |
| `outcome` | 是 | `complete`（全部完成或不适用）、`partial`（仍有未完成）、`waiting`（剩余的都在等时间）、`failed`、`busy`（被占用，什么都没做）、`skipped`（前置不满足，无事可做） |
| `failure_stage` | 否 | `config` / `lock` / `login` / `connect` / `read` / `execute` / `write` |
| `error_type` | 否 | 异常类名（`[A-Z][A-Za-z0-9]{0,63}`），**不要**输出异常正文 |
| `tasks` | 是 | 本阶段每个任务的最终状态（busy、skipped 可为空） |
| `next_wake` | 否 | 需要总控台再来检查的未来时刻（Unix 秒，最多 48 个）；跨轮保留，规则见第 8 节 |
| `metrics` | observe 时必须含 `actions_sent` | 操作指标，见 5.7 |
| `run_scope` | 否 | 仅清单 `run_scope: true` 时生效，≤ 128 KiB，替换后交给下一阶段 |

```json
{"v":1,"phase":"daily","day":"2026-11-17","outcome":"waiting","tasks":{"signin":{"status":"complete"},"mail":{"status":"complete","counts":{"claimed":2}},"energy":{"status":"waiting","current":1,"total":3,"next_run_at":1763344800}},"next_wake":[1763344800],"metrics":{"actions_sent":3,"actions_confirmed":3,"reads":1}}
```

### 5.5 任务状态（十种）

每个任务的状态对象可含：`status`、`reason`（原因码）、`current`/`total`（非负整数；**只有真实分母时才给 `total`**）、`unit`、`next_run_at`（Unix 秒）、`counts`（键必须在 `count_keys` 中；每次带 `counts` 上报，都会整份替换这个任务之前的计数，不合并）。状态或原因码变了却没带 `next_run_at` 时，总控台不再沿用之前的时间，所以换了状态还要等的，要重新给出时刻。

| `status` | 含义 |
|---|---|
| `not_started` | 计划内，尚未处理 |
| `running` | 正在处理 |
| `incomplete` | 部分完成，或仍有可做的部分 |
| `waiting` | 需要等时间（服务器计时、刷新、恢复）；也用于今日已做完（`done_for_today`） |
| `blocked` | 条件不满足（资源不足、未授权等），本轮不再尝试 |
| `complete` | 有服务器证据表明已完成 |
| `failed` | 明确失败 |
| `result_unavailable` | 结果未知：请求已发出未收到结果，或状态读取失败 |
| `unsupported` | 发现了目标，但没有处理流程 |
| `closed` | 今日不适用（未开放、无资格） |

### 5.6 原因码

标准原因码可直接使用：

| 原因码 | 说明 | 原因码 | 说明 |
|---|---|---|---|
| `request_result_missing` | 请求已发出，但未收到结果 | `insufficient_currency` | 货币不足 |
| `action_exception` | 执行时发生异常，未收到成功结果 | `insufficient_stamina` | 体力不足 |
| `timeout` | 执行超时，尚未收到结果 | `insufficient_items` | 道具不足 |
| `session_interrupted` | 会话已中断 | `insufficient_materials` | 材料不足 |
| `session_unavailable` | 当前会话不可用，尚未执行 | `waiting_for_refresh` | 等待服务器刷新 |
| `state_unavailable` | 服务器尚未提供该项状态 | `waiting_for_completion` | 等待服务器任务到期 |
| `login_required` | 需要重新登录 | `waiting_for_stamina` | 等待体力恢复 |
| `captcha_required` | 需要人工验证 | `not_open` | 尚未开放 |
| `rate_limited` | 请求过于频繁 | `forbidden` | 当前授权或规则不允许执行 |
| `server_maintenance` | 服务器维护中 | `config_missing` | 缺少配置或凭据 |
| `unsupported` | 发现目标，但尚无处理流程 | `done_for_today` | 今日已无可做，明日继续 |
| `config_outdated` | 本地配置落后于游戏版本，有新内容不认识（见 3.4 节） | | |

其他原因码写在清单 `reasons` 里。原因码只能是枚举值，**不允许**放服务器消息、异常正文等自由文本。

`window_ended`（今天的开放时段已结束，未完成）由总控台生成，脚本不用上报。

### 5.7 单位、计数与操作指标

- 标准单位：次、项、个、份、轮、件、套、步、封、张、点、宝箱、派遣；其他单位在清单 `units` 中声明。
- 计数只接受 `count_keys` 中的键，值为非负整数；未声明的键会被丢弃，并记一次协议违规（`count_invalid`）。
- 想让服务器错误码显示出来：清单 `units` 里声明 `错误码`（或 `负错误码`），报 `status: "failed"` 时带 `current`（错误码的绝对值）和这个 `unit`，显示为「失败 · 错误码 73」（`负错误码` 显示为「错误码 -73」）。错误码只跟着这一次失败，下一次结果不带就不再显示。

结果 `metrics` 中的操作指标（非负整数）：

| 键 | 含义 |
|---|---|
| `actions_sent` | 发出的变更请求数（领取、购买、提交等）。**observe 时必须上报且为 0** |
| `actions_confirmed` | 收到成功回执的变更请求数 |
| `actions_failed` | 被明确拒绝或失败的变更请求数 |
| `actions_unconfirmed` | 已发出但未收到结果的变更请求数 |
| `reads` | 只读查询请求数 |
| `retries` | 重试次数（含重连） |
| `sessions` | 本次新建的登录会话数 |

## 6. 自检与准入

```bash
python3 run.py check --manifest <目录>/autocontrol.json --static     # 只校验清单
python3 run.py check --manifest <目录>/autocontrol.json --repeat 2   # 只读真实运行两次并打分
```

- `--private <临时目录>` 可以把准入记录写到别处，用于自测。
- 必须项全部通过才会写入准入记录。记录绑定清单内容，清单一改就要重新检查。

### 6.1 自动检查

| 编号 | 级别 | 检查项 |
|---|---|---|
| M1 | 必须 | 接入清单合法（字段、ID、分组、父子关系、调度、占位符） |
| M2 | 必须 | 工作目录存在，启动命令可找到 |
| M3 | 必须 | 只读发现正常结束（退出码 0，未超时、未失败、未被占用） |
| M4 | 必须 | 最终结果符合协议（任务 ID、状态、原因码、单位、计数、指标都合法） |
| M5 | 必须 | 进度事件符合协议：至少一个 `plan`，没有被拒绝的事件，`seq` 递增 |
| M6 | 必须 | 计划覆盖清单中全部固定（`seed`）任务 |
| M7 | 必须 | 只读模式未发出变更请求（`metrics.actions_sent` 存在且为 0） |
| M8 | 必须 | 窗口型任务报 `waiting` 时带 `next_run_at`，且该时刻在 `next_wake` 中（没有窗口型任务时自动通过） |
| M9 | 必须 | 清单声明的 `account_lock` 可以探测：文件不存在，或是本用户可读的普通文件（没有声明时自动通过） |
| S1 | 建议 | 没有输出协议外的字段 |
| S2 | 建议 | 只读发现耗时不超过 `timeouts.observe` 的一半 |
| S3 | 建议 | 结果含 `actions_sent` 和 `reads` |
| S4 | 建议 | 两次只读发现报告的任务集合一致（`--repeat 2`）。每天开放的活动不同不影响：任务集合固定，变的只是状态 |
| S5 | 建议 | 有窗口型任务时，清单声明了 `discovery` 任务，且只读发现上报了它 |

### 6.2 行为要求（评审确认，自动检查无法证明）

| 编号 | 要求 |
|---|---|
| B1 实时读取 | 每次运行都重新读取服务端实时状态来决定做什么；不得依据总控台的展示、归档、指标或本地「今天做过」标记跳过业务 |
| B2 不重放 | 结果不明的变更请求本轮不得重发，如实上报 `result_unavailable` + `request_result_missing`；跨阶段避免重发用 `run_scope` |
| B3 资源互斥 | 同一账号或资源用互斥锁：用 flock 加锁，并在清单 `account_lock` 声明，总控台开轮前会探测它；被占用时以退出码 2 退出且不做任何事，不开第二个会话 |
| B4 有界执行 | 总时长小于 `timeouts.phase`（按实际耗时设，例如平时的两到三倍）；连接和登录有自己的短超时（建议不超过 60 秒，见 3.2 节）；过了 `AUTOCONTROL_DEADLINE` 不再发起新的变更；收到 SIGTERM 后 5 秒内退出，不再发起变更；循环有上限 |
| B5 只读模式 | observe 时零变更请求（包括顺手领取），并上报完整计划 |
| B6 如实上报 | `complete` 必须有服务器证据；部分完成用 `incomplete`；未知用 `result_unavailable`；不适用用 `closed`；不估算进度 |
| B7 隐私 | 事件、结果、退出码里不出现账号、令牌、Cookie、手机号、服务器原始响应、异常正文、用户输入，只用枚举码和数字 |
| B8 服务日 | 以服务器服务日为准返回 `day`；跨服务日的任务归属开始时的服务日 |
| B9 不发通知 | 不自行发送任何通知（飞书或 Lark 机器人、webhook、邮件、短信、推送等），不读取总控台的通知配置；要让人看到的信息只通过事件和结果上报 |
| B10 不自校验代码 | 不做代码签名、重签，也不在启动或登录前核对自身代码文件的哈希；脚本不因自己的代码文件被改动而拒绝运行。代码是否可信由准入和评审负责 |
| B11 花费上限 | 购买、抽卡、付费加速等花费有每日硬上限，上限和今日已用量以服务器读数为准；读不到或读数不可信时不花；余额以服务器回执为准，不用本地扣减代替 |

### 6.3 建议（来自每日复盘，试行）

下面几条来自对已接入脚本的复盘，还在试行，评审时会参考：

| 编号 | 建议 |
|---|---|
| A1 「没有可做」不算失败 | 服务器以「没有可领、次数不足、条件不满足」为由拒绝时不报 `failed`：按情况报 `complete`、`waiting` + `done_for_today`，或 `blocked` + 原因码 |
| A2 已确认的按回执报 | 本轮已收到服务器确认的动作，按回执给出状态，读不到的部分写进 `counts`；不要因为没能回读，就把整个任务报成 `result_unavailable` |
| A3 间接需求核对到具体项 | 以每日任务、红点这类列表为需求方的模块，执行前先确认当天列表里有对应项、而且还有缺口；没有对应项或已经做满就不做 |
| A4 已关闭的玩法不再运行 | 当天不开放、已报 `closed` 的玩法，不要再为它强制新登录、单独唤醒或安排阶段运行 |

## 7. 执行标记与指标

- 任务真正开始执行时调用 `worker.started(task)`，结束时报最终状态；读取状态的时候不要调用它。总控台据此知道哪一项正在执行。
- 运行指标（成功率、超时率、协议违规、未确认请求占比、任务连续失败轮次等）由总控台记录并按阈值监控（`python3 run.py metrics`）。你只需在结果里报 5.7 节的操作指标。
- 完成的统计口径：`complete`、今日已了结（`done_for_today`）、有自己时刻表的阶段今天各时刻都已运行，都算今日完成；`unsupported`、错过窗口的不计；当天还没结束时，未完成的不算进分母。
- 同一任务连续多轮报 `failed` 会被当作需要处理的问题（跨天也接着算，报了别的状态才清零），所以只有真正失败才报 `failed`（见 6.3 节 A1）。

## 8. 常见问题

- **可以打印日志吗？** stdout 可以，但最后一行必须是结果。stderr 的最后 16 KiB 会存到私有目录 `logs/`、保留 7 天，用来排查失败（例如登录报错），不要往里写凭据。自己写的日志文件同样要遵守 B7。
- **一个阶段失败了会怎样？** 记为失败，后续阶段照常运行，不会重放；下一轮会再来。
- **脚本崩溃了要不要自己拉起？** 不要。每个阶段都是一次独立运行，崩溃只算这一阶段失败；总控台自己的调度进程崩溃时也会被自动拉起。
- **怎么让总控台在某个时刻再来？** 在 `plan` 或结果里上报 `next_wake`；任务级时刻用 `next_run_at` 并同时放进 `next_wake`。同一阶段后一次 `plan` 报的时刻会替换它前一次 `plan` 报的；其他阶段报的、以及结果里报的都会保留，所以不要在后面阶段转报前面阶段的时刻。跨轮也一样：一个时刻会一直保留到它到点，或者报它的那个阶段之后又成功跑完一次（届时以它新报的为准）；某一轮失败、或者这一轮没跑到那个阶段，不会丢掉之前报的时刻。所以阶段每次成功跑完，都要把自己还需要的时刻全部重新报一遍。
- **原脚本自带的日报、提醒怎么办？** 全部删掉（B9），改为上报任务状态、原因码和计数。
- **清单改了要做什么？** 重新运行 `check`。通过后，总控台会在两轮之间自动重启这个项目、加载新清单，不用找人重启；前后 10 分钟内有一轮要跑时，它会先等。`run.py projects` 里的「待加载」一行说明还在等什么。准入通过之前，正在运行的调度继续按旧清单跑；它如果因为别的原因重启，会被拒绝启动，直到准入通过。只改执行器代码不用做任何事，下一个阶段启动时就用新代码。总控台自己的代码更新也会这样自动加载：各项目在自己的两轮之间重启一次。只是总控代码换了的，重启时不登录，沿用已保存的进度，等下一轮；清单更新、总控启动或调度异常退出后的重启，会先只读读取一次，不会重放执行。为什么重启、每一轮为什么开，都记在 `~/.config/autocontrol/console/logs/<项目>.log`。
